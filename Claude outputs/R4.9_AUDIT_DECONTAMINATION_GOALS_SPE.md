## 1. VEREDICTO EJECUTIVO

**CONTAMINACION CONFIRMADA — SEVERIDAD MEDIA — LOCALIZADA**

La contaminacion Goals → SPE existe, pero esta **confinada a un unico metodo**: `TripProfitabilityClassifier.classify()`. No afecta al profitabilityScore, no afecta a la decision ACCEPT/REJECT, y no afecta a OpportunityEvaluator. La preocupacion documentada en R1 sobre "sincronizacion de thresholds ProfitabilityConfig desde Goals" es **FALSA** — los thresholds estan hardcodeados y nunca se actualizan desde Goals.

**Impacto concreto:** `profitabilityLevel` (EXCELLENT/GOOD/ACCEPTABLE/BAD) puede variar entre dos conductores con diferente progreso economico ante la misma oferta. Esto viola el principio de determinismo intrinseco establecido en R4.8.

**Solucion recomendada:** Opcion B — Eliminar el parametro `economicContext` de `classify()`. Complejidad: BAJA. Archivos afectados: 2. Lineas modificadas: ~15.

## 5. AUDITORIA: TripProfitabilityClassifier

**Archivo:** `TripProfitabilityClassifier.kt`
**Veredicto:** CONTAMINADO en classify(), CLEAN en calculateScore()

### classify() — CONTAMINADO (lineas 64-93)

**Firma:** `fun classify(metrics, config, decision, pickupDistanceKm, economicContext = null)`

**Punto de contaminacion 1 — Post-target BAD (lineas 74-76):**
```kotlin
if (isTargetReached && targetPaceRatio != null && targetPaceRatio < 0.95) {
    return TripProfitabilityLevel.BAD
}
```
- Cuando el conductor ha alcanzado su meta diaria (`TARGET_REACHED`) y el viaje paga < 95% del ritmo objetivo, se fuerza BAD
- **Efecto:** Un viaje que intrinsecamente es GOOD (cumple todos los umbrales economicos) se degrada a BAD porque el conductor ya cumplio su meta personal
- **Viola determinismo:** Dos conductores — uno con meta cumplida, otro sin meta — ven diferente profitabilityLevel para la misma oferta

**Punto de contaminacion 2 — Contextual EXCELLENT (lineas 86-89):**
```kotlin
val isContextualExcellent = targetPaceRatio != null &&
    targetPaceRatio >= 1.15 &&
    kmRatio >= 1.10 &&
    metrics.netProfit >= config.minNetTripProfit
```
- Si el viaje paga >= 115% del ritmo horario requerido para la meta del conductor, se promueve a EXCELLENT
- **Efecto:** Un viaje que intrinsecamente es GOOD (no alcanza los criterios de isPureExcellent) se promueve a EXCELLENT porque el conductor tiene un requiredHourlyRate bajo
- **Viola determinismo:** Conductor A (requiredHourlyRate=20 €/h) ve EXCELLENT; Conductor B (requiredHourlyRate=35 €/h) ve GOOD para la misma oferta de 30 €/h

**Variables contaminadas derivadas de economicContext:**
| Variable | Fuente | Linea |
|---|---|---|
| isTargetReached | economicContext.dailyProgress.status == TARGET_REACHED | 64 |
| baseGoalHourly | economicContext.dailyProgress.targetEur / plannedHours | 65-66 |
| effectiveRequiredHourly | isTargetReached ? baseGoalHourly : requiredHourlyRate | 70 |
| targetPaceRatio | grossPerHour / effectiveRequiredHourly | 71 |

### calculateScore() — CLEAN

**Firma:** `fun calculateScore(metrics, config, pickupDistanceKm)`

- NO recibe economicContext
- 5 componentes ponderados: hourly(35%), distance(25%), netProfit(20%), pickup(10%), timeUtilization(10%)
- Todos basados exclusivamente en metrics vs config thresholds
- profitabilityScore es **puramente intrinseco**

## 11. FRONTERA: Automatic Mode

**Definicion R4.8:** Automatic evalua la calidad intrinseca de una oferta — maximizar dinero generado minimizando tiempo y distancia. Independiente de Goals, workedHours, plannedHours, remainingHours, requiredHourlyRate, targetPaceRatio, estimatedGoalContribution, progressStatus.

**Estado actual:**
- OpportunityAssessment (quality, recommendation, confidence): **CLEAN** — base para Automatic
- profitabilityLevel en TripEvaluation: **CONTAMINADO** — pero Automatic NO deberia consumirlo (consumira OpportunityAssessment)
- Decision ACCEPT/REJECT: **CLEAN**
- profitabilityScore: **CLEAN**

**Conclusion:** La capa que Automatic mode consumira (OpportunityAssessment) esta limpia. La contaminacion de profitabilityLevel no bloquea la implementacion de Automatic, pero debe corregirse para coherencia arquitectonica y para que Manual mode muestre informacion intrinseca correcta.

## 12. FRONTERA: Manual Mode

**Definicion R4.6/R4.8:** Manual muestra valoracion intrinseca como informacion primaria, con contexto de Goals como informacion separada adicional.

**Estado actual del HUD:**
- `HudVisualTier` (color) depende de profitabilityLevel → **CONTAMINADO**
- Context reasons (CONTEXT_DAILY_TARGET_REACHED, etc.) → **INFORMATIONAL, correcto**
- goalPaceText, goalContributionText, goalStatusText → informacion de Goals, **separada, correcto**

**Problema:** El color del HUD (la senyal visual primaria) mezcla economia intrinseca con progreso de Goals. Un conductor que ya cumplio su meta ve BAD para viajes que intrinsecamente son GOOD. Esto confunde la informacion que Manual mode deberia mostrar como "valoracion intrinseca."

## 13. TWO-DRIVER PROOF

**Escenario:** Oferta de 11.50 EUR, 10 km trip, 20 min, pickup 2 km.
- grossPerHour = 34.50, grossPerKm = 1.15, netProfit = 8.83

**Conductor A** — meta: 160 EUR/8h, workedHours: 4h, earnedEur: 60 EUR, status: BEHIND, requiredHourlyRate: 25.0
- targetPaceRatio = 34.50 / 25.0 = 1.38 → >= 1.15
- isContextualExcellent = true (targetPaceRatio >= 1.15, kmRatio 1.15/1.0 >= 1.10, netProfit 8.83 >= 2.0)
- **profitabilityLevel = EXCELLENT**

**Conductor B** — sin Goals configurados (economicContext = null)
- targetPaceRatio = null
- isContextualExcellent = false
- isPureExcellent: kmRatio 1.15 < 1.25 → false
- isGood: kmRatio 1.15 >= 1.0, hourlyRatio 34.50/24.0=1.4375 >= 1.0, netProfit 8.83 >= 2.0 → true
- **profitabilityLevel = GOOD**

**Conductor C** — meta: 120 EUR/5h, workedHours: 5h, earnedEur: 125 EUR, status: TARGET_REACHED
- isTargetReached = true
- baseGoalHourly = 120/5 = 24.0
- effectiveRequiredHourly = 24.0 (baseGoalHourly porque isTargetReached)
- targetPaceRatio = 34.50 / 24.0 = 1.4375 → >= 0.95, no se fuerza BAD
- isContextualExcellent: targetPaceRatio 1.4375 >= 1.15 → true
- **profitabilityLevel = EXCELLENT**

**Conductor D** — meta: 200 EUR/5h, workedHours: 4.5h, earnedEur: 195 EUR, status: TARGET_REACHED
- isTargetReached = true
- baseGoalHourly = 200/5 = 40.0
- effectiveRequiredHourly = 40.0
- targetPaceRatio = 34.50 / 40.0 = 0.8625 → < 0.95
- **profitabilityLevel = BAD** (forzado por post-target rule)

**Resultado:** Misma oferta (11.50 EUR, 10km, 20min) → 3 resultados diferentes:
- A: EXCELLENT, B: GOOD, C: EXCELLENT, D: BAD

**DETERMINISMO INTRINSECO VIOLADO.** ∎

## 16. OPCIONES DE ARQUITECTURA

### Opcion A — No hacer nada

- Dejar la contaminacion como esta
- Automatic mode consumira OpportunityAssessment (limpio) → no hay problema inmediato
- profitabilityLevel sigue contaminado en TripEvaluation y HUD
- **Pros:** Cero riesgo de regresion, cero esfuerzo
- **Contras:** Deuda tecnica, profitabilityLevel no es fiable como indicador intrinseco, HUD Manual mode muestra informacion enganyosa, violacion de principio R4.8

### Opcion B — Eliminar economicContext de classify() (RECOMENDADA)

- Eliminar parametro economicContext de classify()
- Eliminar lineas 64-76 (isTargetReached, baseGoalHourly, effectiveRequiredHourly, targetPaceRatio, post-target BAD)
- Eliminar lineas 86-89 (isContextualExcellent)
- Mantener isPureExcellent como unico criterio para EXCELLENT
- **Pros:** Minima modificacion (~15 lineas), profitabilityLevel se vuelve puramente intrinseco, coherencia con R4.8, classify() pasa a ser determinista
- **Contras:** Se pierde la "inteligencia contextual" del Level, pero esa inteligencia es precisamente la contaminacion que R4.8 prohibe
- **Impacto en SPE freeze:** classify() NO es parte del contrato SPE 2.0 congelado. SPE 2.0 congelo formulas, pesos, thresholds, 7 hard rules, profitabilityScore. classify() es un clasificador cualitativo separado. La eliminacion del parametro economicContext es **compatible con el SPE freeze**

### Opcion C — Bifurcar classify() en dos versiones

- classify() intrinseco (sin economicContext) para Automatic/base
- classifyWithContext() (con economicContext) para Manual
- **Pros:** Preserva comportamiento contextual para Manual
- **Contras:** Duplicacion de logica, dos Levels en TripEvaluation, complejidad innecesaria. El Level contextual es exactamente lo que R4.8 prohibe — no tiene sentido preservarlo

### Opcion D — Mover logica contextual a GoalContextEvaluator

- GoalContextEvaluator ya existe y ya calcula targetPaceRatio, estimatedGoalContribution
- Mover el "post-target BAD" y "contextual EXCELLENT" a GoalContextMetrics como campos adicionales
- classify() se queda limpio
- Manual mode consume GoalContextMetrics para informacion contextual
- **Pros:** Separacion limpia, reutiliza componente existente
- **Contras:** GoalContextEvaluator se vuelve mas complejo, y la informacion que produciria (contextualLevel?) duplica lo que profitabilityLevel ya hace. Ademas, R4.8 establece que Manual muestra Goal context como informacion separada, no como modificador de Level

## 17. SOLUCION RECOMENDADA: OPCION B

**Razon principal:** La contaminacion en classify() contradice directamente el principio R4.8: "AUTOMATIC NO depende de un objetivo economico configurado" y "RideDecider no necesita conocer su jornada para decidir si un viaje es bueno." Aunque la contaminacion afecta a profitabilityLevel (no a la Decision ni al Score ni a OpportunityAssessment), mantenerla crea incoherencia arquitectonica y un HUD que muestra informacion enganyosa.

La Opcion B es la solucion mas limpia porque:

1. **Minimalismo:** Solo modifica classify(), sin tocar calculateScore(), hard rules, Decision, ni OpportunityEvaluator
2. **Determinismo:** Tras la correccion, `classify(metrics, config, decision, pickupDistanceKm)` produce el mismo resultado para cualquier conductor con la misma config
3. **Compatibilidad SPE:** classify() no forma parte del contrato SPE 2.0 congelado (que cubre formulas, pesos, thresholds, hard rules, profitabilityScore)
4. **Preserva Context Reasons:** Las razones CONTEXT_DAILY_TARGET_REACHED, CONTEXT_ABOVE_REQUIRED_HOURLY_RATE, CONTEXT_BELOW_REQUIRED_HOURLY_RATE en DecisionEngine se mantienen — son informativas y utiles
5. **Preserva GoalContextEvaluator:** El calculador de GoalContextMetrics se mantiene intacto — produce informacion separada para Manual mode
6. **1 test afectado:** Solo `classify_contextualBoosting_whenDrivingTowardDailyTarget_shouldReturnExcellent` debe eliminarse
